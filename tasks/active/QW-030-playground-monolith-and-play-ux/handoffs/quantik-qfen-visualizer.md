  - `src/play.js` — new `fetchCapabilities({ baseUrl, fetch })`: GETs `/api`, and reads its `recording` field defensively — `true` unless the field is explicitly `false`. That single rule covers three distinct cases the packet asked for: an absent field (an older server, per `decisions.md#D6`), a non-2xx response, and a `fetch` that itself rejects (network failure / unreachable service) — all three are caught and turned into `{ recording: true }` rather than propagating an error. `recordGame` gained a `recording` option (default `true`); when false, it returns `{ recorded: false, skipped: true }` without making any request at all.
  - `test/play.test.js` — 7 new tests (one of the packet's three named cases, "recording on → POST happens," was already covered by the pre-existing "recording posts the body..." test, counted here as the 8th): recording declined skips the POST and doesn't throw; recording explicitly on still posts; four `fetchCapabilities` cases (explicit true, explicit false, absent field, HTTP error); and the unreachable-`/api` case using a `fetch` stub that throws `TypeError("Failed to fetch")`, the same error shape a real browser raises for a network failure.
  - `src/app.js` — new module state `capabilities = { recording: true }` (optimistic default, matching D6); new `loadCapabilities()` called once from `bindEvents()` alongside the existing `loadOpponents()`; `recordFinishedGame` passes `recording: capabilities.recording` to `Play.recordGame` and, when the result comes back `skipped`, sets `elements.gameMessage.textContent` to `"Not saved — this server keeps no record of games."` — same element, same non-error styling as "Game recorded." and "Game was already recorded."
- Decisions and assumptions:
  - **`fetchCapabilities` never rejects.** Every failure mode — HTTP error, network failure, a payload that doesn't parse — is caught internally and turned into the same `{ recording: true }` fallback. This was a deliberate design choice beyond what D6 literally states (D6 is about an absent *field*, not an unreachable *server*): the packet's own framing — "a network failure is not evidence of a storeless server" — extends the same optimistic-default logic to the transport failure case, and it means `app.js`'s `loadCapabilities()` needs no try/catch of its own.
  - **Did not add a "the POST itself failed for some other reason" sanitization pass.** V5's scope is specifically the *known-storeless* case (recording explicitly `false`), which is now intercepted before any request is made. A POST that is attempted (because `capabilities.recording` was `true`) and then genuinely fails — a real 500, a CORS misconfiguration — still surfaces `Not recorded: ... failed with HTTP ${status}.`, unchanged from before. That message showing a status code in a *genuine* error case (as opposed to the deliberate-no-store case this item targets) was not in the packet's stated problem and was left alone.
  - Chose to show a message ("Not saved — this server keeps no record of games.") rather than saying nothing, per the packet's stated alternative ("or says nothing") — a plain fact felt more informative than silence, and it fills the same UI slot every other end-of-game outcome already uses, so nothing about the layout needed to change to accommodate it.
